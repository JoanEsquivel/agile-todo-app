# Todo Checklists (Sub-items) — Design Spec

Amends [`2026-08-10-agile-todo-app-design.md`](2026-08-10-agile-todo-app-design.md) (which defined the `Todo` model and completion behavior this spec extends). Board, rollover, and retention behavior from the monthly-board and three-month-window specs is unchanged — this spec only adds a nested checklist to individual todos.

## Scope

Each todo can hold an optional **checklist** of sub-items. On the todo card:

1. A **progress toggle** (e.g. `2/5`) expands/collapses the list.
2. Items are **added, checked/unchecked, and removed inline** on the card — the todo form is untouched.
3. **Completion is bidirectional**: when every item is checked the todo completes itself; unchecking an item reopens it; toggling the todo's own checkbox checks/unchecks the whole list.
4. The Help modal's Guide tab documents the feature.

Out of scope (deliberate YAGNI): renaming items (delete + re-add instead), reordering, per-item priority/dates/reminders, new keyboard shortcuts, persisting the expanded/collapsed state.

## 1. Data model

New type in `src/domain/types.ts`:

```ts
export interface ChecklistItem {
  id: string;
  text: string;
  checked: boolean;
}
```

`Todo` gains one optional field: `checklist?: ChecklistItem[]`.

**No schema bump, no migration.** This follows the documented `Note.rolledOver` precedent: an optional nested field on a value inside `todos` leaves every stored v3 blob structurally valid, `validatePersistedState` never descends into todo fields, and `partialize`/INV-6 govern only top-level `PersistedState` keys. The field carries a comment in `types.ts` recording this reasoning, same as `Note.rolledOver` does. Import validation stays deliberately shallow (that's existing TD-1 territory, not this feature's job).

Rollover and carry-over (`applyRollover`, `carryOverTodos`) spread-and-patch whole todo objects, so the checklist rides along untouched — no change to `rollover.ts` or `fortnight.ts`.

## 2. Domain: `src/domain/checklist.ts`

A new pure module (imports only `./types`; time is a parameter — INV-2/INV-3). All functions take a `Todo` and return a new `Todo`, never mutating.

**The invariant:** for a todo with a **non-empty** checklist, `done === every item checked`, always. A todo with no checklist (or `undefined`) behaves exactly as today. Whenever a function flips `done` false→true it stamps `completedAt = now`; true→false clears `completedAt` — identical semantics to today's manual toggle, regardless of which function did the flip.

- `toggleChecklistItem(todo, itemId, now)` — flips one item's `checked`, then reconciles `done`/`completedAt` per the invariant. Checking the last unchecked item completes the todo; unchecking any item of a done todo reopens it.
- `addChecklistItem(todo, item: { id, text }, now)` — appends the item unchecked, then reconciles: adding an item to a completed todo **reopens it** (the invariant wins). The `id` is generated by the caller (the store, same mechanism as `addTodo`) so the domain stays deterministic.
- `removeChecklistItem(todo, itemId, now)` — removes the item, then reconciles: removing the last *unchecked* item while the rest are checked **auto-completes** the todo. Removing the final remaining item normalizes `checklist` back to `undefined` (never an empty array — an empty array would make `every()` vacuously true) and leaves `done` as it was.
- `setTodoDone(todo, done, now)` — the parent toggle. Sets `done` (+ `completedAt` stamp/clear) and, if a checklist exists, sets **every** item's `checked` to match. This is what makes "check the parent → check all sub-items" and its mirror hold.

**INV-5 consequence, made explicit:** auto-completion makes `done: true` just like manual completion, so the todo stops rolling over and stays pinned to the day/month it completed in. That is the intended behavior (consistent with manual completion), and it gets its own domain test rather than being left implicit.

## 3. Store: `src/store/store.ts`

`done` keeps a single stored source of truth; the store just applies domain functions:

- `toggleDone(id)` — reimplemented as `setTodoDone(t, !t.done, nowIso())`. For checklist-less todos this is byte-for-byte today's behavior.
- New actions, mirroring the domain: `addChecklistItem(todoId, text)` (generates the item id, trims/rejects empty text), `toggleChecklistItem(todoId, itemId)`, `removeChecklistItem(todoId, itemId)`. Each is a thin `set()` wrapper over its domain function with `nowIso()`.

No changes to `updateTodo`'s patch allowlist, `partialize`, migrations, or `importState` (the checklist lives inside `todos`, which `importState` already copies wholesale).

## 4. UI: `TodoItem.tsx` (+ its module CSS)

All new UI lives on the todo card; `TodoForm` is untouched.

- **Progress toggle** — rendered only when the todo has a checklist: a small button showing `2/5` (checked/total) with `aria-expanded` and an accessible name that keeps the visible text as a literal substring (WCAG 2.5.3, same rule as the tape chips): `aria-label` = `"2/5 checklist items done"`. Clicking expands/collapses the list. Expansion is local `useState`, collapsed by default, ephemeral (unmounts with the card; nothing persists).
- **Item list** — a nested `<ul>` inside the card's `<li>` (valid HTML). Each item row: a checkbox whose accessible name is the item text, the text itself, and — only when `!readOnly` — a remove button named `Remove <item text>`. Checked-item styling (strike-through) uses `:has(input:checked)` in the module CSS, not a new `data-*` attribute — INV-13's vocabulary is untouched.
- **Add form** — only when `!readOnly` (INV-9 rule 1: the mutating element itself is gated, not just a trigger): a labeled text input (`Add checklist item`) + button inside the expanded area. Typing in it is safe with the global shortcuts because every shortcut already bails while focus is in a text-entry control.
- **First item** — a todo without a checklist has no counter to expand, so the door in is an `Add checklist` button in the card's existing actions row (next to Edit/Delete, `!readOnly` only): it expands the empty checklist area with the add form focused. Once the first item exists, the counter takes over as the toggle. In read-only mode a checklist-less todo shows nothing new at all.
- **Read-only history mode** — checkboxes render `disabled` (same treatment as the existing done checkbox); add/remove UI doesn't render at all. `readOnly` keeps arriving as a prop from `DayColumn` (INV-9) — never derived inside the component.
- All colors/spacing from `tokens.css`; one colocated module CSS, no `composes:`/`:global` (INV-12).

## 5. Help modal

One new entry in `GUIDE_SECTIONS` (`src/components/help/HelpModal.tsx`), placed immediately after "Todos & priorities". Final copy, every claim verifiable app behavior:

> **Checklists** — "Use a todo's Add checklist action to break it into sub-items, then expand its counter (e.g. 2/5) to add, check off or remove them. When every item is checked the todo completes itself; unchecking an item reopens it. Checking the todo itself checks or clears the whole list."

No Shortcuts-tab change (no new shortcut exists).

## 6. Testing

Per INV-10 (mocked `./clock` module, `2026-08-18` fixtures, role/label queries, colocated grouped files):

- **`src/domain/checklist.test.ts`** (new) — the invariant matrix: check last item → done + `completedAt`; uncheck on a done todo → reopened + `completedAt` cleared; parent toggle checks/unchecks all; add-to-done reopens; remove last unchecked → auto-completes; remove final item → `checklist` undefined, `done` untouched; todos without checklist unaffected by `setTodoDone` beyond today's behavior.
- **Rollover interplay** (in `checklist.test.ts` or `rollover.test.ts`) — a todo auto-completed via its checklist is skipped by `applyRollover` and `carryOverTodos`, exactly like a manually completed one.
- **`src/store/store.test.ts`** — the three new actions wire domain → state; `toggleDone` on a checklist todo syncs the items; empty/whitespace item text is rejected.
- **`src/store/storePersistence.test.ts`** — a todo's checklist survives an export → import round trip.
- **`src/components/todos/todos.test.tsx`** — `Add checklist` creates the first item; counter renders and expands; checking the last item marks the card done (`data-done` appears); unchecking reopens it; add and remove items inline; in read-only history mode the checkboxes are disabled and the `Add checklist`/add/remove UI is absent.
- **`src/components/help/help.test.tsx`** — the Guide tab lists the Checklists section.
